# Checker A/B — the profile cache TTL fault, measured separately

Generated by `scripts/generate_ab_table.py` from `reports/checker_ttl_fault.json`. Every number comes from that file.

The same 50 scenarios (seed 42) were played 2 times against the same running engine at `http://localhost:8000`, for 60s each. The engine was not restarted, rebuilt or reconfigured between arms. The only thing that changed is which pre-fix measurement fault the checker was running with. That engine process was started with `PROFILE_CACHE_TTL_SECONDS=3600`, declared by the operator because this script cannot read the value from the engine.

The engine process behind every arm above was reported by the operator as running with `PROFILE_CACHE_TTL_SECONDS=3600`. The TTL column is what the *harness* planned the run's cache expectations against, which is a separate thing: the pre-fix state had both at 3600s.

## Which checks failed, by name

| Arm | Failed outcomes |

| baseline (current checker) | `fact_retrievable` x4, `profile_refreshed_on_new_fact` x1 |

`fact_retrievable` failures track the extractor, which is non-deterministic across identical inputs, so a small count there moves between runs on its own and should not be read as a fault's effect.

## What each fault was

- **`assume_long_profile_cache`** (fixed in 2132dc8) — the engine's profile cache TTL defaulted to 3600s while runs lasted 60-360s, so checks read a profile cached before the run began (deployment setting, not harness logic)

## Reproducing this

```bash
# the engine must be running
#   started with PROFILE_CACHE_TTL_SECONDS=3600
python3 scripts/run_checker_ab.py --duration 60 \
    --arms baseline,assume_long_profile_cache \
    --engine-profile-cache-ttl 3600 \
    --out reports/checker_ttl_fault.json
python3 scripts/generate_ab_table.py --report reports/checker_ttl_fault.json --out <doc>
```
