# Checker A/B — what the pre-fix harness was measuring

Generated by `scripts/generate_ab_table.py` from `reports/checker_bug_ab.json`. Every number comes from that file.

The same 50 scenarios (seed 42) were played 9 times against the same running engine at `http://localhost:8000`, for 60s each. The engine was not restarted, rebuilt or reconfigured between arms. The only thing that changed is which pre-fix measurement fault the checker was running with. That engine process was started with `PROFILE_CACHE_TTL_SECONDS=30`, declared by the operator because this script cannot read the value from the engine.

## What each fault was

- **`synthetic_fact_ids`** (fixed in 2132dc8) — /ingest was fire-and-forget, so the harness invented sim:<scenario>:<index> ids while the engine stored mem_* ids
- **`compare_utterance_text`** (fixed in 2132dc8) — the harness compared the scenario sentence against the stored 'subject predicate object' triple, scoring 0.500 against a 0.6 bar
- **`silence_is_failure`** (fixed in b779619) — an utterance the extractor found no fact in was reported as a storage failure rather than skipped
- **`script_decides_ownership`** (fixed in b779619) — criterion H was decided by the scenario script's phrasing rather than by who owns the text in memory.db
- **`reuse_run_number`** (fixed in 8a80d91) — every run reused run_number=1, so validation replayed earlier runs out of audit_log.db and manufactured cross-user findings
- **`literal_verdicts`** (fixed in 8a80d91) — the report writer asserted "user_isolation": "PASS" and isolation_pass_rate: 1.0 unconditionally, and decided audit completeness by events_played > 0 rather than by any audit check

## Not measured here

- **`assume_long_profile_cache`** — deployment setting, not harness logic: needs the engine restarted with PROFILE_CACHE_TTL_SECONDS=3600

The engine in these runs was reported by the operator as using a profile cache TTL of 30.0s. This script cannot read that value from the engine, so it is recorded as declared, not measured.

## What the pre-fix report writer would have published

The last two faults were in the report writer rather than in any check, so their effect is not a delta — it is a verdict that ignores the checks underneath it.

On the `literal_verdicts` arm the old writer would have published criterion H as **PASS** with `isolation_pass_rate: 1.0`, while the checks it overrode found 50 passed and 0 failed. Criterion G would have been **PASS** on the basis `events_played > 0`.

On the `all_harness_faults` arm the old writer would have published criterion H as **PASS** with `isolation_pass_rate: 1.0`, while the checks it overrode found 0 passed and 50 failed. Criterion G would have been **PASS** on the basis `events_played > 0`.

## Reproducing this

```bash
# the engine must be running
python3 scripts/run_checker_ab.py --duration 60 \
    --engine-profile-cache-ttl 30
python3 scripts/generate_ab_table.py
```

The `reuse_run_number` arm writes its events against `run_number=1` in `audit_log.db`, which is exactly the fault it reproduces, so that arm's numbers depend on how much history that run number already holds. Every other arm allocates a fresh run number.
