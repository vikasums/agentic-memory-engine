# LongMemEval — first external run

Generated by `scripts/generate_benchmark_doc.py` from `benchmarks/longmemeval/results.json`. Every number comes from that file.

LongMemEval (oracle split) (arXiv 2410.10813 (ICLR 2025)), 500 instances available, 40 run: 20 knowledge-update and 20 abstention. 486 user utterances were ingested in 1183s of wall clock against `http://127.0.0.1:8010`, an engine with its own store at `./benchmarks/data/bench_memory.db`, retrieving `top_k=5`.

**These are not the published LongMemEval scores and cannot be compared to them.** The paper scores a generated answer with an LLM judge. This engine generates nothing, so the metrics here are judge-free proxies at a 0.6 token-coverage bar, defined in `benchmarks/README.md`.

## Knowledge update

| Metric | Value |
| --- | --- |
| Instances | 20 |
| Answer in the top 5 | 15% |
| Answer present in the store at all | 15% |
| Superseded value returned (a stale read) | 0% |
| Instances with any deactivated row | 0% |
| Mean active facts per user | 7.8 |

What the store did with each update:

| Belief state | Instances | Meaning |
| --- | --- | --- |
| `current_value_missing` | 17 | the current value never reached the store |
| `old_value_never_stored` | 3 | current value active, old value absent entirely — the extractor never produced it, so nothing was there to supersede |

So on this data the supersession path fired 0 times and accumulated both values 0 times. Neither number evidences belief revision: the binding constraint is upstream, in extraction. The current value reached the store in 15% of instances, and the v0.3.0 simulation reported the same class of gap (66-69 of 111 utterances yielding no fact). The engine's natural key is `user_id:subject:predicate`, so two statements only collide when the extractor chooses the same predicate for both; on free text it does not.

## Abstention

| Metric | Value |
| --- | --- |
| Instances | 20 |
| Returned at least one memory | 100% |
| Mean memories returned | 4.75 |

These questions are unanswerable from the history. `/retrieve` ranks and returns `top_k` with no confidence floor, so this result is the design and not a regression. It is measured so the gap has a size: the engine has no way to say "I don't know".

## The instances that worked

- `9ea5eabc` — matched on `Paris` via `user recently_visited Paris`, 13 active facts for that user
- `f9e8c073` — matched on `five` via `user attended_sessions five`, 5 active facts for that user
- `41698283` — matched on `a 70-200mm zoom lens` via `user uses 70-200mm zoom lens`, 10 active facts for that user

Read the short ones carefully: a gold answer of one content token is satisfied by that token alone, so `9ea5eabc`, `f9e8c073` is weaker evidence than the coverage figure suggests. This is the proxy's limit, stated rather than smoothed over.

## Reproducing this

```bash
# fetch the dataset and start the benchmark engine: see benchmarks/README.md
python3 benchmarks/longmemeval/run_benchmark.py --engine http://127.0.0.1:8010 \
    --memory-db ./benchmarks/data/bench_memory.db --limit 20
python3 scripts/generate_benchmark_doc.py
```

The extractor is non-deterministic across identical inputs, which is a known open issue, so a repeat run will not reproduce these figures exactly. In an earlier pass over instance `6a1eabeb` the same utterances produced nine active facts including the answer-bearing one; in this run they produced 5, without it.
